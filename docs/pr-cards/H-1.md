Current official Stripe API facts verified 2026-10-14:
- `POST /v1/checkout/sessions` supports `branding_settings`, and the
  image field requires a typed `{type:'file',file:'file_...'}` object.
  One session cannot specify both logo and icon. This implementation
  selects an explicit icon override first, otherwise saved logo first.
- `POST /v1/payment_links` has no public `branding_settings` parameter.
  Payment Links therefore inherit the account Dashboard branding;
  the server never sends an unsupported per-link field.
- `POST /v1/accounts/:id` is documented for *connected* accounts;
  changing an owner's **own** account uses Dashboard. No assumed own-account
  mutation for descriptor, public details, timezone, card safety,
  account branding or invoice defaults. These are observed guides
  and return `done:false`, `changeMade:false` with exact owner steps.
- `GET /v1/invoice_rendering_templates`, retrieve, archive and unarchive
  are native operations, not Dashboard-only.

## Existing integration and implementation contract

- `src/brand/store.js`: allowed kit fields, exact Checkout translation,
  local optimistic revision. `src/db.js`: additive `brand_kits` keyed
  by verified Stripe account and mode; write only for TEST.
- `src/tools/brand-kit.js`: brand_get, brand_upload_image, brand_save_kit,
  brand_preview_checkout. Upload uses the existing bounded, DNS-pinned public
  image fetch; checks magic bytes and image dimensions, selects proper Stripe
  Files purpose, uses native guarded idempotency and file readback.

  sessions inherit saved kit, and explicit call overrides take precedence.
  Exact file purpose is independently checked before create; actual
  `branding_settings` are re-read. No app-created page is rewritten.

  unarchive; guarded portal appearance update; guarded existing payout
  schedule workflow alias. The latter preserves original protection.
