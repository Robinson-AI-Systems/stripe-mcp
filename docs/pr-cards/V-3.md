## V-3a implementation (#59)

- Native TEST-only dev_list_triggers enumerates only customer.created, product.created, price.created and payment_intent.succeeded.
- Native dev_trigger_event(type,requestKey) is a fully guarded defineWrite-v1 write with exact preview, explicit confirmation, idempotency, selected account, app guard and audit.
- Each action creates real TEST source objects with rtc_run and exact durable account-scoped ledger. Price first creates a product; payment success first creates a customer and independently verifies a synthetic fully succeeded incoming TEST card PaymentIntent for $36.
- Stripe events.list searches at most 300 recent entries of the requested type; a positive candidate must match event type, target ID, run metadata, selected account, TEST mode and full payment amount. Independently events.retrieve confirms the same event before event ID is recorded and run completed.
- A missing event is unobserved/unknown, never success or proof of absence. Retry the SAME immutable requestKey and IDs; if an event was durably recorded, retrieve that exact event by ID even when outside the recent listing.
- Events added as immutable TEST ledger type and recognized by V-2 cleanup for ownership checks, but never deleted or reported cleaned automatically.
- Unit actual guarded-handler tests exercise dry-run, unknown types, event delay, replay, provenance, LIVE/read_only, payment amount and V-2 event cleanup behavior. Pinned SDK stripe-mock tests for all used request endpoints. Update registry, profile counts, status, catalog, plan, and work index.

## V-3b — Native TEST update and cancellation events (#60)

Four more provider-generated event types are now supported by the same strict guarded and evidence-verified engine: customer.updated, product.updated, price.updated, and payment_intent.canceled. They are not synthetic event pushes: the source objects are independently verified and durably recorded before safe customer/product/price updates or cancellation of an unconfirmed PaymentIntent.

Every action uses a dedicated stable Stripe idempotency key and independently verifies the changed description/name/nickname/status before claiming the event. Actual event data must have the exact changed attribute as well as type, ID, selected account, TEST livemode and rtc_run. Payment cancellation requires amount_received=0; successful or processing payments are never canceled.

V-3c remains for harder native event situations including invoice.payment_failed, customer.subscription.deleted, charge.dispute.created, and Checkout completion. These will only be listed after real provider behavior is implemented. V-3 stays IN_PROGRESS.

## V-3c1 — TEST subscription created/deleted (#61)

**Drift A.** Stripe subscriptions can auto-create an initial invoice even when a free trial begins, and its ID must not be left untracked. A subscription.created event cannot be treated as equivalent to a billing success. A subscription.deleted event must follow real cancellation without a final invoice or proration, not a fabricated event request.

- Extend the same guarded, idempotent dev_trigger_event to customer.subscription.created and customer.subscription.deleted. A real TEST product, monthly recurring USD price, synthetic customer and seven-day trial subscription are provider-created/tagged/retrieved and durably recorded under one immutable run ID.
- The provider-linked latest_invoice must actually exist, belong to the same TEST customer, be a zero-paid USD invoice, and carry rtc_run metadata. Tag and independently retrieve it if necessary; record exact invoice ID. Incomplete invoice linkage leaves the run incomplete, never claims an event verified.
- For deleted, cancel only a run-owned trialing subscription with invoice_now=false and prorate=false, then independently confirm the canceled state. Retry skips a verified canceled subscription; no card payment, refund, transfer or payout.
- Only complete after a matching Stripe Event from actual list and independent retrieve with exact TEST mode, run metadata, subscription ID, customer, price and correct trialing/canceled status. Missing asynchronous event remains running and resumable, not an inferred success.
- Tests: real guarded handler delays and retry, subscription/invoice ledger, missing invoice fails closed, no duplicate provider creation or cancellation, pinned SDK recurring price, trial, invoice metadata and cancel shapes. Existing eight event paths retain their immutable plan hashes.
- V-3c2 still needed for genuine invoice.payment_failed, charge.dispute.created, Checkout lifecycles and other events, subject to actual provider methods and safety controls. V-4 forwarding follows V-3.


## V-3c2 — Zero-value invoice created/updated/finalized Events (#62)

- Current-native TEST \`invoice.created\`, \`invoice.updated\`, and \`invoice.finalized\` are triggered by real provider actions on a uniquely tagged synthetic TEST customer/invoice. The invoice is created with no lines, USD zero amount, \`auto_advance:false\`, and collection method \`send_invoice\`. No card, bank debit, email send or payment is initiated.
- On \`invoice.updated\`, mutate only the unfinalized draft description; on \`invoice.finalized\`, finalize with \`auto_advance:false\`, accepting independently verified paid/open zero amount. Original created event requires a draft invoice.
- Exact provider ID, zero amount_due and amount_paid, customer, rtc_run metadata and status must match both source read-back and the independently retrieved Stripe Event snapshot. Events that lag remain unobserved/incomplete and are retried by stable requestKey, never forged.
- Unit guarded-handler tests cover each type, zero dollars, denied foreign provenance, read-back and safe replay without duplicate provider mutations. Official pinned SDK/stripe-mock tests validate invoice create/update/finalize and Events list/retrieve.
- Still to build: provider-real payment failures, disputes and Checkout completions with verified prerequisites and no fake event delivery. V-3 remains IN_PROGRESS; V-4 follows upon acceptance.
