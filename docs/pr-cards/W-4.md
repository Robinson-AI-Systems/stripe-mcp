## Original acceptance and implementation

- Identify an eligible actual selected TEST subscription by a verified exact customer ID; multiple eligible subscriptions require a specific subscription ID. Refuse missing, canceled, foreign, incomplete or currency-ineligible inputs.
- Show one finite preview for the actual customer/subscription, timing (`now` requires `invoiceNow` and `prorate`, `period_end` forbids them), optional exact charge refund with provider-confirmed remaining USD, and optional up to five verified open, unpaid manual invoice voids. Each child step is independently dry-run through its wrapped native handler before any writes.
- Require a fresh matching SHA-256 plan token, independent explicit `confirm` and stable operation-specific request keys. Child writes use original `payment_create_refund`, `billing_cancel_subscription` and `invoice_void` guards, not direct provider SDK calls. A refund always keeps its **separate owner money-out authorization**, $500/day shared account limit, native app refund exception and readback; other app changes continue to require `outsideApp` when an app owns the record.
- Execute in refund → cancel → void order; stop at first denied, uncertain or unconfirmed child and report the verified completed operations and remaining ones without automatic replay or blanket success. The workflow is not an atomic transaction. Avoid claiming future final invoices can be pre-voided: `invoiceNow:true` with `voidOpenInvoices:true` is deliberately refused. No LIVE.
- Tests: `tests/unit/workflow-customer-actions.test.js`, registry exact tool-set/write-contract assertions, and normal exact-head CI. Protected native TEST acceptance remains queued after checked release; no owner money-out approval was granted merely for source implementation.

## Safety and provider prerequisites

Actual original Stripe TEST provider execution and any safe disposable refund/cancel/void acceptance require separate selected-account owner-approved fixtures and the original per-money-out authorization. Full code + CI is not proof of real-world processing. The financial provider's return can be pending; a confirmed refund creation does not claim bank settlement. No automated replay of an uncertain child or cleanup.
